# 产品远景与使命文档

## 1. 一句话产品定位

`Game Server Hub` 是一个面向中小团队与个人服主的、自托管优先的 DST 服务器全生命周期控制面板，覆盖实例创建、安装、运行、监控与运维闭环。

## 2. 核心用户群体与痛点

### 2.1 目标用户

- **独立服主/小型社群管理员**：需要快速搭建并稳定维护 DST 联机服务器。
- **轻量工作室运维**：希望统一管理测试服、活动服、长期存档服。
- **技术型玩家社区**：追求可控、可扩展、可审计的自托管方案。

### 2.2 主要痛点

- **部署门槛高**：SteamCMD、目录结构、端口、防火墙配置链路长且容易出错。
- **运维碎片化**：安装日志、实例状态、资源指标分散在命令行与系统工具中。
- **操作不一致**：启动、停止、更新、重装流程缺少标准化与可回放记录。
- **多能力耦合**：实例管理、系统管理、控制台能力边界不清，学习成本高。

## 3. 产品长期远景与短期目标

### 3.1 长期远景（3-5 年）

- 成为可扩展的多游戏自托管控制面板底座，支持适配器化接入不同游戏。
- 形成分层能力：Community 提供可用核心，Pro 提供自动化、审计、企业集成。
- 提供标准化运维体验：可观测、可审计、可回滚、可复制。

### 3.2 短期目标（v1）

- 交付 DST 单游戏、单节点（`local-node`）可用闭环。
- 完成实例生命周期核心路径：创建 -> 安装 -> 启停 -> 更新 -> 删除。
- 提供系统级基础能力：面板设置、SteamCMD 配置与安装、主机资源与网络信息。
- 明确规划态模块（Mod、备份、配置中心、文件、计划任务、通知审计）的边界与接口预留。

## 4. 核心价值主张（差异化优势）

- **DST 专注优化**：将 DST 的目录与配置约束收敛为可视化流程。
- **容器化运行时统一**：以 Docker 作为主执行面，降低宿主机污染与漂移风险。
- **前后端同仓与契约同源**：便于快速迭代与功能追踪。
- **规划与实现分层清晰**：通过 TODO/FDS 明确标记已实现、部分实现、规划态，避免“文档已完成但能力未交付”。

## 5. 产品边界声明（当前版本）

- v1 仅支持 DST（`gameCode=343050`）。
- v1 仅支持本地节点主路径，远程多节点能力为后续迭代范围。
- 房间（Cluster）与世界（Shard）在文档层区分，当前实现仍以单分片可运行闭环为主。
- Pro 商业化策略已预留，不作为 v1 发布阻断项。

## 6. 成功指标（v1）

- **功能闭环**：创建、安装、启停、更新、删除全链路可通过验收剧本。
- **稳定性**：实例关键操作成功率达目标阈值，失败可定位到日志与错误码。
- **可运维性**：系统信息、安装日志、实例控制台日志可用于排障。
- **可维护性**：文档与代码事实保持一致，规划态能力有明确落点与里程碑。

## 7. 版本叙事原则

- 用“已实现 / 部分实现 / 规划态”三态表达，不使用含糊状态。
- 对外材料不夸大多节点与多游戏能力。
- 文档引用以 `docs/TODO.md` 与 `docs/FDS/*` 为执行与设计主索引。
